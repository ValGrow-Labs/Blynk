## The seven items
1. **No time limit.** New setting `sms_sending` (system_configurations, JSON): `{ any_time: true, quiet_hours: { enabled: false, start: '22:00', end: '07:00' } }`. Default any_time true and quiet hours off, so by default nothing is blocked by the clock. `assertSmsSendingWindow` is replaced by one function `smsSendAllowed(settings, now)` used by immediate offers, test SMS, scheduled and automatic campaigns and the birthday text. Quiet hours (when the admin switches them on) are Asia/Colombo wall-clock, may wrap midnight; a scheduled or automatic run that falls inside quiet hours is DELAYED to quiet-hours end (not dropped); an immediate offer inside quiet hours is refused with a clear message. The old `store_sms.sms_on_closed_days` switch stays in the data (and its UI card text must say it is replaced by 'SMS sending rules', or the card is removed from Opening hours: builder decides, keeping old data readable) but no longer blocks anything when `any_time` is true.
2. **Fully customised text.** Placeholders in any text: `{name}` (customer's first name; when missing: 'friend' / 'මිත්‍රයා' / 'நண்பரே' by language), `{points}` (points balance), `{wallet}` (wallet balance, 'LKR 1,250'), `{app_link}` (https://blynk.lk/app). Rendered per recipient at queue time. Unknown placeholders are rejected on save with the list of allowed ones. Parts are estimated on the longest plausible rendering. Saved **templates** (`sms_templates`: name + si/ta/en texts): CRUD, picked in the compose screens. Max rendered text 480 chars per language as today.
3. **Schedule.** An offer can be sent later: `send_at` (ISO, Asia/Colombo shown to staff, must be in the future, up to 1 year). Implemented as a campaign of kind ONCE.
4. **Automatic repeats.** Campaign kind RECURRING: DAILY at HH:mm, WEEKLY on chosen weekday(s) at HH:mm, MONTHLY on a day 1-28 at HH:mm; optional starts_on / ends_on; audience re-evaluated at every run (e.g. 'ordered in the last 30 days' every Friday 6 PM).
5. **Automatic triggers.** Campaign kind TRIGGER, checked once a day at a chosen HH:mm: `DAYS_AFTER_LAST_ORDER` (N days since the customer's last placed order; once per such order), `DAYS_AFTER_SIGNUP` (N days after sign-up, optionally only if they never ordered), `NO_ORDER_FOR_DAYS` (lapsed: no order for N days, repeat at most every `cooldown_days`, default 30). Each with its own si/ta/en text. Idempotency per customer per anchor so a customer never gets one trigger twice for the same anchor.
6. **Better audiences.** Extend `customer-groups.ts` with a `CUSTOM` group (existing groups unchanged; push broadcasts keep working, and may also accept CUSTOM): filters, all optional, AND-ed: `areas` (delivery address area/town names that exist in addresses), `min_orders`/`max_orders` (delivered orders), `min_spend_lkr` over `spend_days`, `language` (si/ta/en/none), `min_points`/`max_points`, `last_order_days_min`/`last_order_days_max`. A live preview endpoint returns recipient count, parts, cost estimate in parts, language split and 3 sample renderings.
7. **Campaign history and controls.** `sms_campaigns` + `sms_campaign_runs`: every run records time, recipients, parts, skipped (opted out / capped / no phone), status. Staff can pause, resume, edit (future runs only) and cancel a campaign; the list shows next run time and totals. Immediate offers keep their own history (`sms_offers`) and show in the same history list.

## Limits (all optional, admin-decided, settings key `sms_limits`, default everything off)
`{ per_customer: { enabled: false, max: 1, days: 7 }, monthly_budget: { enabled: false, parts: 5000 } }`. Per-customer cap counts SMS_OFFER outbox rows (offers and campaigns, not order/OTP texts) to the same user inside the rolling window: capped customers are skipped and counted as `skipped_capped`. Monthly budget counts SMS parts queued for offers and campaigns in the current Asia/Colombo calendar month: when a send would exceed it, an immediate offer is refused with the remaining parts; a campaign run is skipped (status BLOCKED_BUDGET) and the campaign stays active for the next period. Opt-outs (`users.sms_offers_opted_out_at`) always apply, as today.
