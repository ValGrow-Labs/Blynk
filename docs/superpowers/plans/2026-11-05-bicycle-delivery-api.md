# Bicycle delivery: backend API as built (2026-11-05)

Backend done (tsc clean, tests/bicycle-delivery.test.ts 43/43). Migration 067 adds orders.delivery_method (owner runs in Coolify; the API is safe to deploy before it: reads coalesce to MOTORBIKE, `ready:false` on the setting).

## Setting - GET and PUT /api/v1/admin/settings/bicycle-delivery (ADMIN + OPERATIONS)
Both return `{ success:true, data:{ enabled:false, max_km:3, fee:{ base_lkr:80, base_km:2, per_km_lkr:30, max_fee_lkr:null }, rider_pay:{ mode:'FIXED'|'PER_KM', fixed_lkr:50, base_lkr:30, per_km_lkr:15, min_lkr:null }, updated_at:null|ISO, ready:true } }`.
PUT takes any subset of `{enabled,max_km,fee,rider_pay}`; a section is replaced whole (send the whole section); strict keys; the merged result is validated, so enabling with an invalid fee/pay gives 400 and changes nothing. Limits: max_km 0.5-10 (1 decimal); fee.base_km 0.5-10 (1 decimal); every LKR amount 0-1000 (2 decimals); max_fee_lkr and min_lkr may be null. `ready:false` = migration 067 not run yet (show a plain note, keep the card usable but tell staff the owner must run the update). Rider pay: min_lkr applies to PER_KM only. FIXED -> fixed_lkr; PER_KM -> base_lkr + per_km_lkr x road km.

## Customer: GET /orders/checkout-info -> `bicycle`
`bicycle: { available:boolean, reason?:string, fee_lkr, charged_fee_lkr, max_km, distance_km|null, distance_estimated|null }`. fee_lkr = standard bicycle fee; charged_fee_lkr = after free-delivery rules (0 when free). Reasons (show `reason` text when not available and the block is worth showing - normally just hide the bicycle card): "Bicycle delivery is not available right now." / "Choose a delivery address to see bicycle delivery." / "Bicycle delivery is for trips up to {max_km} km." / "No bicycle rider is available right now."
POST /orders accepts optional `delivery_method: 'MOTORBIKE'|'BICYCLE'` (default MOTORBIKE). Unavailable -> 400 code BICYCLE_UNAVAILABLE, message "<reason> Please choose motorbike delivery." POST /orders/validate-coupon accepts optional `delivery_method` too and shows the bicycle fee. The charged delivery_fee / standard_delivery_fee on the order are the bicycle fee.
`delivery_method` ('MOTORBIKE'|'BICYCLE') is on: placement response, customer order detail + list, staff order list / packing queue / order detail (top-level field), rider job list + detail (on the delivery), GET /admin/riders/live `unassigned_orders[]`, GET /admin/riders/suggestions response.

## Staff: switch to motorbike - POST /api/v1/admin/orders/:id/delivery-method (alias /api/v1/orders/:id/delivery-method), ADMIN + OPERATIONS
Body `{ "method": "MOTORBIKE" }`. 200 `{success:true,data:{order}}` (staff order detail). Errors: 404 ORDER_NOT_FOUND; 409 ALREADY_MOTORBIKE "This order is already a motorbike delivery."; 409 ORDER_NOT_SWITCHABLE "The delivery method can only be changed before the order is picked up." (allowed: PLACED, ITEM_UNAVAILABLE, PACKED); 409 ORDER_PAID_CANNOT_SWITCH "This order was paid online or with the Blynk Wallet, so its delivery fee can't change. Cancel it and ask the customer to order again with motorbike delivery." (also any non-COD order). Success recomputes fee/total, releases an assigned/accepted bicycle rider, texts the customer. Show the server message to staff on any error.
The confirm step in the UI should state the new total (the response gives it; before confirming, show text like "The customer's delivery fee changes to the motorbike fee and any assigned bicycle rider is released. The customer is sent a text.").

## Assignment
A BICYCLE order assigned to a non-bicycle rider -> 409 RIDER_NOT_BICYCLE "This is a bicycle delivery, so it can only be given to a rider who delivers by bicycle." (show server message). GET /admin/riders accepts optional `?order_id=<id>`; for a BICYCLE order it lists only bicycle riders - use it wherever the rider picker for an order is built. Suggestions already list only bicycle riders for a bicycle order.
